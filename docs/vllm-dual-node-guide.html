0流程总览（重启后要做的全部事情）

预检查（两台）：GPU 空闲、驱动正常、无残留 ray/vllm 进程、网络互通。原因见 §1。
.153 起 head：ray start --head --node-ip-address=192.0.2.10 --port=6379，注意先 export NCCL 变量。原因见 §2。
.154 加入集群：ray start --address=192.0.2.10:6379 --node-ip-address=192.0.2.20，同样先 export NCCL 变量。
验证（.153）：ray status 必须看到 2 个节点、16 GPU，才能进行下一步。
只在 .153 启动 vLLM：bench 或 serve，带 --tensor-parallel-size 16 --distributed-executor-backend ray。原因见 §3。
为什么重启后要全部重做：Ray 的 head/worker 进程和 vLLM 引擎都是普通用户态进程，重启后全部消失，没有任何开机自启。而且启动顺序有依赖：worker 加入需要 head 的 6379 端口先就绪，vLLM 需要集群里凑够 16 张 GPU 才会开始加载模型。顺序错了不是报错就是挂起。

1预检查（两台都要做）

两台各执行一次
# 1. GPU 驱动正常且显存为 0（重启后若有残留进程会占用显存导致加载失败）
nvidia-smi --query-gpu=index,name,memory.used --format=csv,noheader

# 2. 确认没有残留的 ray / vllm 进程
pgrep -af "raylet|vllm" | grep -v grep

# 3. 端口 6379 没被别的程序占用（只在 .153 上需要为空）
ss -lntp | grep 6379

# 4. 两台互通（在 .154 上执行，反向同理）
ping -c 3 192.0.2.10

# 5. 模型目录存在（两台都要有，原因见 §6.4）
ls /data/Qwen3-32B/config.json

# 6. conda 环境完好、版本一致
/root/anaconda3/envs/vllm/bin/python -c "import vllm,ray;print(vllm.__version__,ray.__version__)"
为什么要逐项检查： ① 显存不为 0 说明有残留计算进程，vLLM 按 --gpu-memory-utilization 申请显存时会直接 OOM 失败； ② 残留的 raylet 会让新集群组不起来（端口冲突或节点注册混乱），必须 ray stop --force 清掉； ③ 6379 是 Ray 集群的"注册大门"（GCS 端口），被占用则 head 起不来； ④⑤⑥ 是双机特有的坑——网络不通、某一台缺模型文件、两台 vLLM/Ray 版本不一致，都会在启动中期才报出很难定位的错。

2启动 Ray 集群（先 head 后 worker）

2.1 在 192.0.2.10 上启动 head 节点

在 .153（server03）上执行
# ★ 第一步：进入 vllm 环境（base 环境里有个不完整的 ray，会报 No module named 'msgpack'）
conda activate vllm

# 清理可能的残留（没有也不会报错）
ray stop --force 2>/dev/null

# ★ 关键：NCCL 变量必须在 ray start 之前 export（原因见下方说明）
export NCCL_DEBUG=INFO \
       NCCL_IB_DISABLE=0 \
       NCCL_IB_HCA="mlx5_0,mlx5_1,mlx5_2,mlx5_3,mlx5_4,mlx5_5,mlx5_6,mlx5_7" \
       NCCL_IB_GID_INDEX=3 \
       NCCL_SOCKET_IFNAME=enp225s0f0 \
       NCCL_NET_GDR_LEVEL=5 \
       NCCL_P2P_LEVEL=SYS \
       NCCL_CROSS_NIC=1

ray start --head --node-ip-address=192.0.2.10 --port=6379
为什么每个参数都不能省：
  • --head：声明这是主节点，在本机启动 GCS（集群注册中心）。
  • --node-ip-address=192.0.2.10：本环境最容易踩的坑。两台机器都是 K8s 节点，kube-ipvs0 上挂了 30 多个 10.68.x.x IP，还有 flannel.1、cni0、docker0 等虚拟网卡。Ray 自动探测本机 IP 时很可能选中虚拟网卡的地址，head 会把一个别人根本路由不到的 IP 广播出去，worker 永远加不进来。显式指定后强制走物理网卡 enp225s0f0 的地址。
  • --port=6379：固定 GCS 端口，worker 加入、排错（telnet/ss）都以它为准。
  • NCCL 变量为什么要在 ray start 前 export：vLLM 的 16 个 worker 进程是 Ray 的 raylet 守护进程派生的，worker 的环境变量继承自 raylet，而不是你后来敲 vllm 命令的那个 shell。所以这些变量必须存在于 raylet 启动时的环境里，否则 worker 里的 NCCL 会拿默认值去选网卡（很可能选到 cni0/flannel），表现为卡在 NCCL 初始化几十分钟不报错。

2.2 NCCL 环境变量速查

变量作用 / 不设的后果
NCCL_SOCKET_IFNAME=enp225s0f0bootstrap 与控制通道只走这块 10G 物理网卡。不设则 NCCL 按网卡名排序自动挑，本机会挑中 docker0/cni0 等虚拟网卡 → 双机握手失败或卡死。
NCCL_IB_HCA=mlx5_0,...,mlx5_7限定用 8 张 400G mlx5 网卡做跨机数据传输。不设可能选中错误的网口。
NCCL_IB_GID_INDEX=3RoCE 网卡一个口有多个 GID（对应不同服务等级/路由），实测 index 3 才是本机房可互通的那个。
NCCL_IB_DISABLE=0显式允许使用 IB/RoCE（默认即允许，写出来防止环境里有反向配置）。
NCCL_NET_GDR_LEVEL=5开启 GPU Direct RDMA（GPU 显存 ↔ 网卡零拷贝），跨机 AllReduce 吞吐的关键。
NCCL_P2P_LEVEL=SYS / NCCL_CROSS_NIC=1允许跨 PCIe/NUMA 的机内 P2P；允许多网卡间负载分担。均为已验证的性能配置。
NCCL_DEBUG=INFO排查期强烈建议开着：日志会打印每条通道走了哪块网卡/哪种传输（如 via NET/IB/8/GDRDMA），出问题时一眼定位。稳定后可去掉以减少日志量。

3启动 vLLM（只在 .153 上执行）

为什么只在 head 上敲命令：vLLM 的驱动进程只在 .153 启动一次，它通过 Ray 把 16 个 worker（两台各 8 个）调度起来；.154 上不需要、也不应该手动执行任何 vllm 命令——那样会起一个独立的单机实例，反而占卡冲突。

3.1 方式一：离线基准测试（推荐重启后先跑这个验证链路）

在 .153 上执行 · 2026-10-27 实测通过的完整命令
conda activate vllm   # 别在 base 里跑

# NCCL 变量这个 shell 里也 export 一份（覆盖驱动进程本身）
export NCCL_DEBUG=INFO NCCL_IB_DISABLE=0 \
       NCCL_IB_HCA="mlx5_0,mlx5_1,mlx5_2,mlx5_3,mlx5_4,mlx5_5,mlx5_6,mlx5_7" \
       NCCL_IB_GID_INDEX=3 NCCL_SOCKET_IFNAME=enp225s0f0 \
       NCCL_NET_GDR_LEVEL=5 NCCL_P2P_LEVEL=SYS NCCL_CROSS_NIC=1

vllm bench latency \
  --model /data/Qwen3-32B \
  --tensor-parallel-size 16 \
  --distributed-executor-backend ray \
  --input-len 1024 --output-len 128 --batch-size 16
三个关键点：
  • 子命令必须是 latency（或 serve/throughput 等）：vllm bench <模型路径> 这种写法会报 invalid choice，模型要用 --model 传。
  • --distributed-executor-backend ray 不能省：TP=16 大于本机 8 卡，不指定会立刻报 World size (16) is larger than the number of available GPUs (8)。这个参数就是告诉 vLLM"去 Ray 集群找卡，别只在本地找"。
  • 启动约需 3 分钟（权重加载 27s + 编译/CUDA graph ~2.5min），日志出现 Warming up... 和进度条即正常，耐心等。

3.2 方式二：在线服务（vllm serve）

在 .153 上执行
vllm serve /data/Qwen3-32B \
  --served-model-name qwen3 \
  --host 0.0.0.0 --port 8000 \
  --max-model-len 32768 \
  --max-num-seqs 300 \
  --gpu-memory-utilization 0.85 \
  --tensor-parallel-size 16 \
  --distributed-executor-backend ray

启动完成的标志：日志出现 Uvicorn running on http://0.0.0.0:8000 / Application startup complete。

3.3 验证服务真的跑在双机上

# 功能验证（任意机器执行）
curl http://192.0.2.10:8000/v1/chat/completions \
  -H "Content-Type: application/json" \
  -d '{"model":"qwen3","messages":[{"role":"user","content":"你好"}],"max_tokens":50}'

# 双机验证：两台的 GPU 都应该在跑（各 8 张、显存 ~90GB）
ssh 192.0.2.10 nvidia-smi --query-gpu=index,memory.used --format=csv,noheader
ssh 192.0.2.20 nvidia-smi --query-gpu=index,memory.used --format=csv,noheader

# 集群资源占用：GPU 应显示 16/16

为什么要看两台 GPU：curl 能出结果只证明服务通了；只有确认 .154 的 8 张卡也加载了权重，才能证明张量并行真的跨机了（否则可能是配置错误退化成了单机）。这是双机验证的"金标准"。

4停止与清理

两台都执行
# 1. 停 vLLM（在跑 serve/bench 的 .153 上；bench 跑完会自动退出，无需处理）
pkill -f "vllm serve" ; pkill -f "vllm bench"

# 2. 停 Ray（两台都要）
ray stop --force

# 3. 确认 GPU 显存归零、无残留进程
nvidia-smi --query-gpu=index,memory.used --format=csv,noheader
pgrep -af "raylet|vllm" | grep -v grep
注意顺序：先停 vLLM 再停 Ray。直接 ray stop 会把 worker 连同引擎一起杀掉，虽然也能停干净，但 vLLM 驱动进程可能留下孤儿进程占着显存，所以停完务必用第 3 步确认显存归零。

6原理详解：为什么必须这样做

6.1 为什么 vLLM 双机必须用 Ray，不能用 mpirun？

mpirun 适合的场景（如 nccl-tests 的 all_reduce_perf）：16 个进程彼此完全对等、没有主从，mpirun 只负责把进程拉起来，进程间用 NCCL 自举就能组网。所以你用 mpirun 测 NCCL 是通的——这证明网络层（IB/RoCE、GDRDMA、路由）没有任何问题。

vLLM 的架构不同：它有一个"驱动进程"负责 HTTP 服务、调度、batch 组装，再把算子分发给 16 个 TP worker。驱动与 worker 之间除了 NCCL 数据面，还需要一条控制通道（下发任务、传 KV cache 元数据、收集结果）。这条控制通道由 Ray 提供——包括跨机进程编排、GPU 资源记账（哪台还剩几张卡）、actor 生命周期管理。mpirun 给不了这些，两台各自 vllm serve 也只会变成两个互不相干的单机实例。

6.2 环境变量的继承链：为什么 export 必须在 ray start 之前

进程环境变量的继承关系是固定的：

你的 shell（export NCCL_...）
   └─ ray start → raylet 守护进程（★ 继承 shell 的环境）
        └─ RayWorkerProc / vLLM worker（★ 只继承 raylet，不知道你后来的 shell）
你的另一个 shell（敲 vllm serve/bench）
   └─ vLLM 驱动进程（继承这个 shell 的环境）

也就是说：worker 进程的环境来自 raylet 启动那一刻。如果你先 ray start、后 export，那么 .154 上的 8 个 worker 拿不到任何 NCCL 变量，NCCL 会自行挑网卡——在装了 K8s 的机器上大概率挑中虚拟网卡，然后卡死在初始化。这就是"变量顺序"如此重要的原因。验证方法见 §5 第 4 行。

6.3 为什么要显式指定 node-ip-address：K8s 虚拟网卡的干扰

两台机器的网络接口远不止物理网卡：kube-ipvs0（30+ 个 Service IP）、flannel.1、cni0、docker0、若干 docker bridge。Ray 和 NCCL 的"自动选 IP/网卡"逻辑在这种机器上不可信：一旦 head 把 10.68.x.x 或 162.30.x.x 这类集群内部地址广播出去，对端根本无法回连。显式指定 --node-ip-address（Ray）和 NCCL_SOCKET_IFNAME（NCCL）就是把选择权从"猜"变成"定"。

6.4 为什么模型要在两台都有、之前 file:// 方式为什么失败

① 模型双副本：/data 是各自的本地 NVMe（不是 NFS）。Ray 调度 worker 到 .154 时，worker 是在 .154 本地按相同路径读权重——路径两边一致（/data/Qwen3-32B）即可，这比 NFS 更快也避免锁竞争。

② file:// 初始化失败的原因：早期双机尝试在 /tmp 下留了 vllm_dist_* 文件，这是 PyTorch 分布式 FileStore 的产物——用本地文件当分布式会合点。/tmp 两台不共享，第二台进程永远等不到第一台写入的信息，rendezvous 无限挂起。跨机会合必须走网络（Ray 方案里由 Ray + TCPStore 完成），这就是当时"双机就出问题"的直接原因之一。
